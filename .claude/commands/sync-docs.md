## 컨텍스트

- 최근 커밋: !`git log --oneline -25`
- 마지막 CLAUDE.md 수정 이후 바뀐 파일: !`git diff --name-only $(git log -1 --format=%H -- CLAUDE.md)..HEAD -- 'src/*' 'build.gradle' 'docker-compose.yml' | head -50`
  - ⚠️ 이 목록은 **참고용 힌트일 뿐 검사 범위가 아니다.** CLAUDE.md는 한 섹션만 고쳐도 커밋 시각이 갱신되므로, 손대지 않은 나머지 섹션의 노후는 이 diff에 절대 잡히지 않는다. 실제로 이 문서의 최대 드리프트(ES "미착수")도 이 diff 밖에 있었다. **반드시 문서 전체를 검사할 것.**
- 마이그레이션 목록: !`ls src/main/resources/db/migration`

## 임무

CLAUDE.md의 주장을 **실제 코드로 검증**해서 틀린 곳을 고친다. 대상 섹션: $ARGUMENTS (비어 있으면 전체)

CLAUDE.md는 사람이 손으로 쓰는 문서라 코드보다 항상 뒤처진다. 이 문서가 틀리면 Claude Code가 **이미 있는 걸 또 만들거나, 없는 필드를 참조하는 코드**를 쓴다. 그래서 "그럴듯한 설명"이 아니라 "코드와 일치하는 설명"만 남겨야 한다.

### 절차

1. CLAUDE.md를 읽고, **검증 가능한 사실 주장**을 뽑아낸다. 특히 아래 유형을 우선한다:
   - 상태 주장 — "미착수", "진행 중", "비활성", "리팩토링 필요", "주석 처리됨"
   - 구조 주장 — 엔티티 필드/관계, 패키지 구성, 클래스 이름과 역할
   - 계약 주장 — API 경로, 쿼리 파라미터, 기본값, 응답 형태
   - 커맨드 주장 — 빌드/테스트/실행 명령, 인프라 요구사항
2. 각 주장을 코드에서 확인한다. **추측 금지** — 반드시 파일을 읽어 근거를 확보한다.
   - "미착수"라고 적힌 기능은 특히 의심할 것. 해당 이름으로 Grep/Glob 해서 실제로 없는지 확인한다.
   - 엔티티 필드는 클래스와 `db/migration`의 DDL을 **둘 다** 본다. 마이그레이션에서 DROP된 컬럼이 문서에 남아 있는 경우가 잦다.
3. 어긋난 항목을 **표로 보고**한다: `CLAUDE.md 주장 | 실제 코드 | 근거(file:line)`
4. 각 항목을 실제 코드에 맞게 고친다. 고칠 때:
   - 코드를 읽으면 알 수 있는 내용은 굳이 늘리지 않는다. **왜 그렇게 했는지(설계 의도·트레이드오프·함정)**를 남긴다 — 이게 CLAUDE.md의 존재 이유다.
   - 기존 문서의 서술 톤과 구조(한국어, `**선택 | 왜**` 표 형식)를 유지한다.
   - 섹션을 통째로 지우지 말고 현재 상태를 반영해 다시 쓴다. 없어진 기능은 삭제하되 왜 없앴는지 한 줄 남긴다.
5. 문서에 **아예 빠진 것**도 찾는다: 새로 생긴 패키지·의존성·API·인프라 요구사항 중 CLAUDE.md에 흔적이 없는 것.
6. 마지막에 **새로 쓴 주장을 다시 검증**한다. 드리프트를 고치면서 새 드리프트를 만들면 의미가 없다.

### 하지 말 것

- 코드를 고치지 마라. 이 커맨드는 **문서만** 건드린다. 코드 쪽이 잘못됐다고 판단되면 고치지 말고 보고만 한다.
- 확인 못 한 내용을 채워 넣지 마라. 모르면 모른다고 보고한다.
- 파일 나열식 요약("이 패키지엔 X, Y, Z가 있다")으로 문서를 늘리지 마라. Claude Code는 파일 목록을 스스로 볼 수 있다.
